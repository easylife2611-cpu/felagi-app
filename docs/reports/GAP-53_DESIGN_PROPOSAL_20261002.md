## 4. Proposed Flow (for design review)

### 4.1 Actors

- **User**: loses TOTP device / recovery codes
- **Main Admin**: authorized recovery operator
- **System**: audit + notification

### 4.2 Steps (proposed)

| Step | Actor | Action | System |
|---|---|---|---|
| 1 | User | Submit recovery request via support (S021) | Create recovery ticket, notify Main Admin |
| 2 | System | Identity verification challenge (email OTP + Telegram) | Log AuthAttempt |
| 3 | Main Admin | Review ticket | View identity evidence |
| 4 | Main Admin | Reauth (5-min window) | RequireReauth middleware |
| 5 | Main Admin | Approve recovery | Mark ticket approved |
| 6 | System | Reset user 2FA enrollment state | User must re-enroll TOTP |
| 7 | System | Notify user (Telegram + email) | OutboxEvent |
| 8 | User | Re-enroll TOTP (WP-13c-BE API) | New secret, no old bypass |
| 9 | System | Audit full chain | AuditLog hash chain |

### 4.3 Security properties

- No plaintext secret reset (user re-enrolls)
- Main Admin reauth required for HIGH-risk action
- Full audit trail (who approved, when, why)
- Rate-limited (per user, per admin)
- User notified on both channels
- Old recovery codes invalidated
